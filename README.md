# CyberArk CP Wrapper for Java Applications on AIX

A ksh startup wrapper that integrates a legacy Java application with **CyberArk Credential Provider (CP)** without modifying the application. Designed for applications that read their password from a properties file and whose source code is not available.

## Problem

A JAR running on AIX reads a database password from a plain-text properties file. This is a security finding, but the application cannot be changed to call the CyberArk SDK directly.

## Solution

The application is started through a wrapper script that:

1. Refuses to start if an instance is already running
2. Validates the properties template
3. Retrieves the password from the CyberArk Vault using the CP command-line SDK (`clipasswordsdk`)
4. Validates and escapes the password for the Java properties format
5. Generates the properties file with owner-only permissions (600)
6. Starts the JAR exactly as before and verifies the process is alive
7. Masks the password in the properties file once the application has started

The JAR itself is never touched. The real password exists on disk only during the startup window, readable only by the application's OS user. Password management and rotation move to the Vault.

## How it works

```
app.properties.tmpl  ──(script replaces __PASSWORD__)──►  app.properties  ──►  Java app
       ▲                                                        │
  permanent on disk,                                 regenerated on every start,
  contains no password                               password masked after startup
```

- `app.properties.tmpl` is the only permanent configuration file. It is a copy of the original properties file with the password value replaced by `__PASSWORD__`. **Edit this file to change any setting.**
- `app.properties` is generated by the script on every start and must not be edited manually; it is overwritten each time.
- The Java application keeps reading `app.properties` as it always did. It is unaware of the template.

## Prerequisites

- IBM AIX with ksh (script is ksh88 compatible and uses only native AIX commands; no GNU tools required)
- CyberArk CP (AIM) installed and registered to the Vault; the CP service (`aimprv`) must be running
- An Application ID defined in the Vault, authenticated by OS user and the full path of the wrapper script
- The AppID added to the account's Safe with **Retrieve accounts** permission
- The account (e.g. the DB service user) onboarded in the Vault

## Installation

1. Copy `cyberark-wrapper.sh` to the application directory, e.g. `/opt/myapp/cyberark-wrapper.sh`.
2. Create the template from the existing properties file:
   ```ksh
   cp /opt/myapp/conf/app.properties /opt/myapp/conf/app.properties.tmpl
   ```
   Edit `app.properties.tmpl` and replace the password value with `__PASSWORD__`. The key must appear exactly once.
3. Remove the real password from `app.properties` (it will be regenerated by the script).
4. Set ownership and permissions:
   ```ksh
   chown appuser:appgroup /opt/myapp/cyberark-wrapper.sh /opt/myapp/conf/app.properties.tmpl
   chmod 750 /opt/myapp/cyberark-wrapper.sh
   chmod 600 /opt/myapp/conf/app.properties.tmpl
   ```
5. Update whatever currently starts the application (`/etc/inittab`, SRC subsystem, `/etc/rc.d` script, cron, or manual procedure) so that it calls `/opt/myapp/cyberark-wrapper.sh` instead of `java -jar` directly.

## Configuration

All settings are variables at the top of `cyberark-wrapper.sh`:

| Variable | Description |
|----------|-------------|
| `APP_HOME` | Application base directory |
| `JAR`, `JAVA_OPTS` | JAR file and JVM options, copied from the current startup command |
| `PROPS` | Properties file read by the application |
| `TEMPLATE` | Template file containing `__PASSWORD__` |
| `PASS_KEY` | Property key holding the password (e.g. `db.password`) |
| `SDK` | Full path to `clipasswordsdk` (default `/opt/CARKaim/sdk/clipasswordsdk`) |
| `APPID`, `QUERY` | CyberArk Application ID and Safe/Object of the account |
| `LOG`, `PIDFILE` | Output log and PID file locations |
| `START_WAIT`, `MASK_WAIT` | Delays before the liveness check and before masking the password |

If the application is managed by AIX SRC, see the note in step 7 of the script.

## CyberArk setup

1. **PVWA → Applications**: create the AppID. Under *Authentication*, add:
   - OS user: the user that runs the wrapper
   - Path: `/opt/myapp/cyberark-wrapper.sh` (optionally with hash)
2. **Safe members**: add the AppID with *Retrieve accounts* (and *List accounts*). Add the CP provider user as well.
3. **Platform policy**: generate printable ASCII passwords with no leading or trailing spaces. The wrapper validates this and refuses to start otherwise. Backslashes are allowed (the wrapper escapes them), but excluding them keeps things simpler.

## Testing

Before using the script, verify CP access manually as the application user:

```ksh
/opt/CARKaim/sdk/clipasswordsdk GetPassword \
   -p AppDescs.AppID=MyApp \
   -p Query="Safe=AppSafe;Folder=Root;Object=db-prod-svc" \
   -o Password
```

This prints the password in clear text; run it only in an authorized session and do not capture it in logs.

If the password is returned, run the wrapper and confirm:

- `ps -p $(cat /opt/myapp/app.pid)` shows the Java process
- the application connects to the database
- after `START_WAIT + MASK_WAIT` seconds, `app.properties` shows `db.password=__REMOVED__`
- running the wrapper a second time is refused with "already running"

**Important test**: break and restore the DB connection while the application is running. If the application fails to reconnect, it re-reads the properties file at runtime; in that case remove step 9 from the script so the password stays in the (600-protected) file during runtime.

## Password rotation

When the CPM rotates the password in the Vault, the running application still holds the old password in memory until restarted. Options:

- Schedule rotation to coincide with a planned restart window
- Use a dual-account setup on the database side
- Trigger a restart from the CPM change process

## Optional: keeping the password off physical disk

If the security requirement is "the password must never be written to persistent storage" (rather than "no static password in configuration"), two options exist:

- **JVM parameter**: if the application accepts the properties file path via a `-D` option or argument, point it to a file on an AIX RAM disk (`mkramdisk`) and generate the file there.
- **Symlink**: if the path is fixed, replace `conf/app.properties` with a symlink to a file on a RAM disk. The application keeps reading the same path.

Both require the RAM disk to be created at boot before the application starts, and must be validated on the actual AIX version. Note that RAM-based storage does not protect against system dumps or privileged users.

## Troubleshooting

| Symptom | Likely cause |
|---------|--------------|
| `Failed to retrieve password from CyberArk CP` | CP service not running, AppID not authorized on the Safe, wrong Safe/Object name, or caller user/path does not match the AppID authentication rules |
| `Expected exactly one '...' line in template` | Key name in `PASS_KEY` differs from the template, or the key appears more than once |
| `Password has leading/trailing spaces` / `non-ASCII` | Adjust the CyberArk platform policy for this account |
| `Application already running` | A previous instance is up, or a stale process; stop it before restarting |
| Application starts but cannot connect to DB | Wrong `PASS_KEY`; inspect the generated `app.properties` right after start |
| Application loses DB connection later | Application re-reads the file at runtime; remove step 9 |
| `cannot load module` from `clipasswordsdk` | Non-standard CP installation; add the CP lib directory to `LIBPATH` |

## Security notes and limitations

- The password is never stored permanently on disk; it is present in the properties file only between generation and masking (`START_WAIT + MASK_WAIT` seconds), or during runtime if step 9 is removed.
- The generated file is owner-only (600) from the moment it is created (`umask 077`, old file removed first).
- The password is never passed as a command-line argument, so it does not appear in `ps` output.
- Clearing shell variables shortens the lifetime of in-memory copies but is not a guaranteed secure wipe.
- The running Java process holds the password in memory; this is inherent to the approach and cannot be avoided without changing the application.
- Overwriting or removing a file does not guarantee that all copies are gone: exclude `app.properties` from backups and consider file system snapshots and system dumps in the risk assessment.
- The residual risk should be documented and formally accepted by the security/audit team.
